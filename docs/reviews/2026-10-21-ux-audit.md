# oob-console UX audit

**Target:** detached checkout of `main`, run with `make dev` (https://127.0.0.1:8443/) against the two built-in mock BMCs (iDRAC8 "Storage node R730XD", iDRAC9 "Edge node R240")
**Date:** 2026-10-21
**Evaluator:** WebUX agent (review only: no tracked file was changed and nothing was committed)
**Evidence:** `screenshots/` next to this file. 150 PNGs named `<page>-<viewport>-<scheme>.png`. The viewports are desktop 1440x900, tablet 820x1180, phone 390x844 and `w320` 320x640, each in dark and light.

**Method.**
- **Crawl:** Playwright 1.63.0 (Chromium) from a scratch directory outside the repo. One real sign-in with a computed TOTP, then the session was reused across 3 viewports x 2 colour schemes for every reachable page: 26 routes, including the enrolment link, the token and user reveal pages, the step-up page and the error pages.
- **Automated accessibility:** axe-core 4.13.0 with tags `wcag2a/aa`, `wcag21a/aa`, `wcag22aa` and `best-practice`, run on 144 page/viewport/scheme combinations.
- **Manual probes:**
  - keyboard tab order (25 stops);
  - WCAG 1.4.12 text-spacing override;
  - 320 px reflow;
  - touch-target and font-size measurement;
  - non-text contrast of form fields, computed from the CSS tokens;
  - server response time per page.
- **Context:** the audit drew on the PRD, the 2026-10-21 layout review (and its Status column), settings_design, console research, task_list P2–P5 and tech_doc §1/§13/§16.

**Not covered:**
- Viewer and operator sessions (only `admin` exists in the dev harness).
- A real stale or no-data server: the mocks can't be stopped from outside. The earlier review simulated this state, and the code path was reviewed.
- Paging over 50 log entries.
- A screen reader pass (VoiceOver/NVDA). axe and a DOM review are not a substitute; do one before the public release.

## 1. Executive summary

| | |
|---|---|
| **Overall UX score** | **66 / 100** |
| **Accessibility (WCAG 2.2 AA)** | **B+**. axe found 0 violations and no page scrolls horizontally, at any width (all 144 scans, including best-practice). Manual checks found a likely 1.4.11 failure (form-field boundaries at about 1.3–1.5:1), log tables that are unusable at 320 px, and a redundant-entry issue in enrolment. |
| **AODA / Canadian compliance** | No blockers for a self-hosted tool. To let adopting organisations meet AODA/IASR, add an accessibility statement and a feedback channel (§6). |
| **Critical (sev 4)** | 0 |
| **High (sev 3)** | 6 |
| **Medium (sev 2)** | 16 |
| **Low (sev 1)** | 7 |

The earlier layout review did its job. Navigation, staleness, the no-data vocabulary, contrast, focus, the error pages and About are now solid, and the app is fast: every page renders in 7–11 ms from cache, well inside the Doherty threshold. **The remaining problems are about what the operator sees first when something is wrong, and about patterns the dangerous features will inherit.**

1. **The server page is not anomaly-first.** On a phone the first screen shows no sensor data at all: the header, the poll metadata and an "Actions" card listing four features that do not exist yet fill it. Below that, 33 "power-good" voltage rows reading `1.00 V` take about half of the R730XD page (`server-r730xd-desktop-dark.png`, `server-r730xd-phone-firstscreen-dark.png`).
2. **"Needs attention" contradicts Events.** The overview says "Nothing needs attention", while the Events page shows two *Warning* login-lockout alerts from the previous 24 h and a history of *Critical* chassis-intrusion events. There is no "recent events" signal and no acknowledge model.
3. **Destructive account actions are one click,** with no confirmation and no undo: Disable account, Reset authenticator, Revoke token. The step-up page does not say *what* you are authorising. These are the patterns power off, fan override and console will copy, so they must be fixed before P2.
4. **The open-source polish gaps are about help, not chrome.** There is no Help or docs link, no first-run guidance, no glossary (SEL, Lifecycle, FQDD, PG), and no "Open BMC web UI" escape hatch. The audit log and the firmware inventory still read like developer output.

The **design brief (§5)** and **acceptance criteria (§6)** turn these into a target for the visual designer. They include a full spec for the confirm, step-up and console patterns that P2–P5 need.

**Laws of UX.**
- **Doherty: passes,** at 7–11 ms server time.
- **Fitts: mixed.** Primary buttons are full width on mobile. But breadcrumb links are 17 px tall and "Firmware inventory" is 18 px: they pass WCAG 2.5.8 through spacing, but are weak for a phone-first stress tool.
- **Hick: fails on the server page.** Every sensor table has equal weight.
- **Miller: fails in the Voltages and Events tables.** These are 33 and 46 undifferentiated rows.
- **Jakob: good.** The page follows OpenBMC/iDRAC conventions: Overview, Hardware, Logs, Inventory.
- **Aesthetic-usability:** the app is clean and credible, but it carries no brand. Trust cues are present: freshness, version, audit chain.

**Gestalt.**
- Cards group sections well (common region).
- *Proximity* breaks in two places: the "Add a user" inline form puts Role's label lower than Username's (`settings-users-desktop-light.png`), and the Audit filter labels sit on different baselines.
- The poll line on the server page sits between the tabs and the cards, so it reads as belonging to neither.

## 4. Findings (prioritised)

Severity uses Nielsen's scale: 4 catastrophe, 3 major, 2 minor, 1 cosmetic. Screenshot paths are relative to this file.

### Severity 3: fix before P2 or before the public release

#### UX-01 · Server page: the first screen is metadata and a placeholder, not health
- **Page:** `/servers/{id}` (Hardware). **Heuristics:** H8, H1, Fitts. **Evidence:** `screenshots/server-r730xd-phone-firstscreen-dark.png`, `screenshots/server-r730xd-desktop-dark.png`.
- **What happens:**
  - On a 390 px phone, header (210 px) + breadcrumb + h1 + rollup + tabs + "Polled at…" + "Last poll took 5 ms" + the auto-refresh form + the **Actions** card fill the entire first viewport. Not one temperature, fan or PSU value is visible.
  - The Actions card has four bullets that each say "not available yet". It is the most prominent card on the page and none of it can be acted on.
  - On desktop it pushes Temperatures down by 240 px.
- **User impact:** someone checking a hot or beeping server on a phone has to scroll before seeing any reading. Under stress this is the costliest place to add friction.
- **Recommendation:**
  1. Remove the Actions card until P2. Put the capability notes on the Inventory tab, under "Capabilities".
  2. When P2 arrives, render actions as a compact **action bar in the page header** (see the brief, C-10), not as a card.
  3. Put a **status summary** directly under the h1: health, power, hottest temperature against its warning threshold, fans N/N, PSUs N/N, draw, and data age.
  4. Then show the **exceptions list** (any non-OK sensor, with an anchor link), then the tables.
  5. Collapse "Polled at… / Last poll took…" into one age chip in the header (UX-16).

#### UX-02 · 33 power-good voltage rows dominate the page and are shown as volts
- **Page:** `/servers/{id}`. **Heuristics:** H2, H8, Miller. **Evidence:** `screenshots/server-r730xd-desktop-dark.png` (Voltages runs from y≈830 to y≈1620 of 2000 in the scaled image), `screenshots/server-r240-phone-light.png` (14 rows reading "Not reported").
- **What happens:**
  - iDRAC "… PG" sensors are boolean power-good signals. The page lists 33 of them as `1.00 V` with an OK badge.
  - On the R240, 14 of 15 read *Not reported*.
  - This is the largest section of the page, and its information content when healthy is a single bit.
- **Recommendation:**
  1. Split the rails into **analog rails** (PSU line voltage, VCORE VR) and **power-good signals**.
  2. Summarise the power-good signals as "Power-good: 33/33 OK". Put the full list in a no-JS `<details>`, and expand it automatically when any signal is non-OK.
  3. Show a PG reading as "Good" or "Fault", never as `1.00 V`.
  4. Hide an all-*Not reported* column, and say so once ("This BMC reports power-good state only").

#### UX-03 · Thresholds are numbers, not headroom; tables are not anomaly-first
- **Page:** `/servers/{id}`, overview cards. **Heuristics:** H6, H1, ops pattern "anomaly-first". **Evidence:** `screenshots/server-r730xd-desktop-dark.png`, `screenshots/overview-desktop-dark.png`.
- **What happens:**
  - Temperatures show Reading / Warning / Critical as three separate numbers, so the operator does the subtraction (47 °C vs 87 °C).
  - Rows are sorted by location and name, not by severity.
  - The overview card says "Hottest CPU 47 °C" with no indication of whether that is good.
- **Recommendation:**
  1. Add a **headroom meter** per temperature row: an inline bar marked at the warning and critical thresholds, with a text equivalent, for example "40 °C below warning". CSS-only bars are possible with `<meter>`, which is accessible and needs no JS.
  2. Sort non-OK rows first.
  3. On the overview card, show "47 °C · 40° headroom", with the badge coloured by the worst headroom.
  4. Keep the numeric columns for experts.

#### UX-04 · "Needs attention" ignores recent events
- **Page:** `/` vs `/events`. **Heuristics:** H1, ops "status at a glance", trust. **Evidence:** `screenshots/overview-desktop-dark.png` says "Nothing needs attention…". `screenshots/events-desktop-dark.png` shows two **Warning** "Login attempt alert for root … IP will be blocked" entries about 10 h before the page was generated, and a run of **Critical** "The chassis is open" SEL entries.
- **What happens:** Needs attention is computed only from the current sensor health. A BMC lockout, an intrusion or a PSU AC-loss that self-recovered never reaches the overview.
- **User impact:** the overview can say "all clear" while the evidence of an incident is one click away. That trains users to stop trusting the overview.
- **Recommendation:**
  1. Add a second block, "**Recent events (last 24 h): N warning, N critical**", with links to `/events?severity=warning&since=24h`.
  2. Later, add a per-user "seen up to" marker ("3 new since your last visit") and an **Acknowledge** action (audited) for critical SEL entries.
  3. Make the empty-state copy honest: "No sensor problems. 2 warning events in the last 24 h."

#### UX-06 · Destructive actions are single-click, with no confirmation and no undo
- **Page:** `/settings/users/{id}`, `/settings/tokens`. **Heuristics:** H3, H5. **Evidence:** `screenshots/settings-user-detail-desktop-dark.png`; code `templates/settings_user.html` (Disable and Reset submit directly) and `settings_tokens.html:16` (Revoke submits directly).
- **What happens:**
  - "Disable account" and "Reset authenticator and create link" act on the first click. Reset ends sessions and invalidates the authenticator, so it is irreversible.
  - "Revoke" on a token silently breaks a dashboard or monitor that uses it, and it is a small quiet button next to the token name.
  - Meanwhile "Change role" is the full-width *primary* button, even when the role hasn't changed. Hierarchy is inverted: the safe action shouts and the dangerous ones whisper.
- **User impact:** a mis-tap on a phone locks a colleague out or breaks a dashboard integration. The same pattern applied to *Force off* on the firewall would take the internet down.
- **Recommendation:**
  1. Add a **server-rendered confirmation interstitial** (`GET …/confirm`, then `POST`), which needs no JS. It states the consequence in one sentence, names the target, and makes **Cancel** the default focus.
  2. Use **typed-name confirmation** for irreversible or high-blast-radius actions (Reset authenticator, Revoke a token used in the last 24 h, all P2 force actions).
  3. Disable "Change role" until a different role is selected. Show what each role can do beside the select.
  4. Show the token's *last used* time on the revoke confirmation ("Last used 2 min ago from 192.0.2.45").
  5. This is the **C-11 Confirm** component in the brief.

#### UX-07 · The step-up page has no context, and it shows a form even when no step-up is needed
- **Page:** `/stepup?next=…`. **Heuristics:** H1, H4, H5. **Evidence:** `screenshots/stepup-desktop-dark.png`.
- **What happens:**
  - The heading is "Confirm it is you", with no mention of *what* is being confirmed.
  - When the window is already fresh, the page says "You can already make changes until 02:49:21" **and** still shows an autofocused code field and a primary Confirm button.
  - It also restates the 5-minute window in prose that will be wrong if the setting changes.
- **Why it matters for P2:** FR-8 requires step-up plus a typed name for power actions. An operator who sees a context-free code prompt cannot tell a legitimate prompt from a confusing one, and can't check that the action is the one they intended.
- **Recommendation:**
  1. Pass and render the pending action: "**Power off · Edge node R240** needs a fresh code." Show the action's consequence line and the server's critical tag.
  2. When the window is already fresh, redirect straight to `next`, or show only a Continue button.
  3. Show the remaining window as a time ("valid until 02:49 UTC"), taken from config rather than hard-coded.
  4. Spec: brief C-12.

### Severity 2: next phase

#### UX-05 · Events: informational events labelled "OK", repeat noise, no default triage view
- **Page:** `/events`, `/servers/{id}/logs`. **Heuristics:** H2, H8, Miller. **Evidence:** `screenshots/events-desktop-dark.png`.
- "Unable to log in for root…" carries an **OK** badge, the same green badge as a healthy fan. Informational is not the same as healthy.
- 7 of 46 rows are "The previous log entry was repeated N times".
- The page has 46 rows and no default filter.
- **Recommendation:**
  1. Introduce an **Info** severity, styled neutral, for log entries. Reserve OK for health.
  2. Fold "repeated N times" into the row above as "x23".
  3. Default `/events` to **Warning and above, last 7 days**, with an "All" link.
  4. Add the per-server severity and text filter (old F-07, deferred).
  5. On phones, render logs as stacked cards (see UX-09).

#### UX-08 · The phone header takes a quarter of the screen; the Servers menu overlaps Sign out and can't be dismissed
- **Page:** all pages at ≤ 40 rem. **Heuristics:** H3, H8, Fitts. **Evidence:** `screenshots/overview-phone-dark.png` (header ≈ 210 px of 844), `screenshots/servers-menu-open-phone-dark.png` (dropdown drawn over "Sign out", with no backdrop).
- **Recommendation:**
  1. On phones, show a single-row header: brand + current section + a **Menu** `<details>` that opens a full-width sheet containing the nav, the server list (with health), the user, and Sign out.
  2. Close it by navigation. Accept that a `<details>` won't close on Escape without JS, or add a tiny optional script; the brief allows one.
  3. Keep the 44 px targets.

#### UX-09 · Log tables are unusable at 320–390 px
- **Page:** `/servers/{id}/logs`. **Heuristic:** WCAG 1.4.10 (data tables are exempt, but usability fails). **Evidence:** `screenshots/server-r730xd-sel-w320-viewport-dark.png`. Only Time and half of a Severity badge are visible. The Message is off-screen inside the scroll region, and the page is 6,333 px tall.
- **Recommendation:** at ≤ 40 rem render each entry as a stacked item: severity badge + time on line 1, message on line 2, meta on line 3. The old review's "stacked rows" option should be applied to logs and events specifically.

#### UX-10 · Firmware inventory is unreadable for its main question ("is anything out of date or pending?")
- **Page:** `/servers/{id}/inventory`. **Heuristics:** H2, H8. **Evidence:** `screenshots/server-r730xd-inventory-desktop-dark.png`.
- Nine rows are named "Component 101068" and similar.
- The FQDD column is *Not reported* on every row.
- States Current / Installed / Previous are unexplained, and they conflict: Component 101434 is 2.25 *Current* and 2.23 *Installed*.
- **Recommendation:**
  1. Group the table by component.
  2. Show *Running* (Current) prominently, *Staged* only when it differs, and *Previous* (rollback) in muted text.
  3. Map Dell component IDs to names where known, and fall back to "Unnamed component (ID 101068)".
  4. Hide columns that are empty on every row.
  5. Add a one-line legend for the states.

#### UX-11 · The audit log reads like a database dump
- **Page:** `/settings/audit`. **Heuristics:** H2, H8. **Evidence:** `screenshots/settings-audit-desktop-dark.png`.
- Details are raw JSON, wrapped mid-token (`"UT C"`, `"ad min"`).
- The Principal column reads "anonymous via local", "cli via system" and "admin admin".
- Action codes are shown without labels, and the filter labels sit on misaligned baselines.
- **Recommendation:**
  1. Render a human sentence first: "admin created API token **homepage** (expires 2027-01-19)". Put the code (`token.create`) in a muted monospace chip.
  2. Show details as a key/value list.
  3. Show "Unknown user" for anonymous principals.
  4. Wrap only at word boundaries (`overflow-wrap: anywhere` only on hashes).
  5. Make the filters a single-row toolbar with aligned labels.

#### UX-12 · Secret reveal pages: proportional font, no usage hint
- **Page:** token reveal, user-created reveal. **Heuristics:** H5, H10. **Evidence:** `screenshots/token-reveal-desktop-dark.png`, `screenshots/user-created-reveal-desktop-dark.png`.
- The token `oobk_F5aeqng77zObelhQ…` is set in the UI sans-serif, where `l`, `I` and `1` are ambiguous.
- There is no copy affordance, and nothing says *how* to use the token: header name, endpoint, or a Homepage/Kuma snippet.
- **Recommendation:**
  1. Use a monospace secret field.
  2. Add an optional **Copy** button (progressive enhancement: one `'self'` script, which CSP allows; nothing breaks without it).
  3. Add a usage block: `Authorization: Bearer <token>` + `GET /api/v1/servers`, with links to the integration docs.
  4. On the user-created page, show the link's expiry, and give a "Send this link to *ops.viewer*" instruction.

#### UX-13 · Enrolment asks for the password again right after it was set; no step indicator
- **Page:** `/enroll/{token}` → reveal. **Heuristic:** WCAG 3.3.7 Redundant Entry (A); the security exception is arguable, because the single-use link already authenticates. Also H5. **Evidence:** `screenshots/enroll-reveal-phone-light.png`.
- **What happens:**
  - The user sets a password on step 1. Step 2 asks for username (prefilled) + password + code again.
  - There is no "Step 2 of 2".
  - The secret is not grouped into 4-character blocks.
  - "Do not share or screenshot it" sits directly above a QR code the user is told to scan.
- **Recommendation:**
  1. In the link flow, confirm with **code only**: the session is bound to the redeemed link.
  2. Add a stepper ("1 Password · 2 Authenticator · 3 Done").
  3. Group the manual secret into blocks of 4.
  4. Reword the warning to "Only you should see this code. Don't send it to anyone."
  5. End on a success page with a "Sign in" button, rather than relying on the redirect.
  6. Separately: `/enroll` has page title "Set up your authenticator" but h1 "Finish setting up your authenticator" (`screenshots/enroll-desktop-dark.png`).

#### UX-14 · The rate-limit message gives no wait time

## 5. Design brief for the visual designer

### 5.1 Product in one line
A calm, trustworthy, self-hosted cockpit for out-of-band management of a handful to a few dozen servers. It is opened mostly **when something is wrong**: a server is down, hot or beeping. Its job is to answer three questions in under five seconds: *Is anything wrong? Where? Can I trust this data?* It then gives a safe path to act: power, fans, console.

### 5.2 Personas

| Persona | Context | Needs | Fears |
|---|---|---|---|
| **P1 Homelab operator under stress** (primary) | Phone or laptop, often away from the rack, adrenaline, possibly on a slow remote link | Instant health verdict, hottest sensor, PSU state, recent critical events, then power cycle or console | Acting on stale data; powering off the wrong box (for example the firewall); locking themselves out |
| **P2 Small-IT operator** (operator role) | Desktop during work hours, 5–30 servers, ticket open | Fleet table, filter to problems, SEL for a ticket, graceful restart, serial console | Doing something only an admin should do; lacking an audit trail for the ticket |
| **P3 Admin / maintainer** | Desktop, calm, occasional | Users, tokens, servers, audit verification, version, upgrade info | Misconfiguring TLS pins; a token leaking; unclear audit entries |
| **P4 Read-only viewer / NOC screen** | A wall display or a family member's phone | A glanceable overview that auto-refreshes and is clearly marked when stale | Being shown "OK" when the data is old |
| **P5 Open-source evaluator** | First 10 minutes after `docker run` | Understand what it is, sign in, add a server, see data | Dead ends, jargon, a missing "how do I…" |
| **P6 Assistive-technology user** (cross-cutting) | Screen reader, keyboard-only, 200–400 % zoom, colour-vision deficiency, cognitive load from stress | Text equivalents for every status, predictable order, no time pressure except deliberate, labelled windows | Colour-only status, focus traps in the console, timeouts during typed confirmation |

### 5.3 Primary tasks, ranked

1. **Triage the fleet**: what is wrong, where, and how fresh is the data? *(Overview)*
2. **Diagnose one server**: worst sensor vs threshold, fans, PSUs, recent critical events. *(Server › Hardware, Logs)*
3. **Act safely**: graceful restart or power on (operator); force off or power cycle (admin); end or start a fan lease. *(P2/P3)*
4. **Get hands on the box**: serial console (operator), graphical console (admin). *(P4/P5)*
5. **Read and export history**: SEL or Lifecycle for a ticket; the audit trail of who did what. *(Logs, Events, Audit)*
6. **Administer**: invite or disable users, mint or revoke tokens, (later) add servers and confirm TLS pins. *(Settings)*
7. **Check version and licences, and get help.** *(About, Help)*

### 5.4 Information hierarchy per page (top = first seen)

**Global shell.**
- Brand, instance name, Overview · Servers ▾ · Events · Settings (admin) · Help, then the user menu (name, role, preferences, sign out).
- A global **data-freshness indicator**, plus a **banner slot** for system problems: "Log server delivery failing", "TLS pin changed on R240, polling paused".
- Phone: one-row header + Menu sheet.

**Overview.**
1. Fleet verdict line: "All 12 healthy · data 15 s old", or the summary strip when not all OK.
2. **Needs attention**, combining (a) non-OK and stale sensors and (b) Warning+ events in the last 24 h, with acknowledge later.
3. **Active operations**: running fan leases with countdowns, open console sessions, power actions in their cooldown window. *(P2+)*
4. Servers as cards (≤ 6) or a table (> 6, sortable), each with health, power, hottest temperature with headroom, fans N/N, PSUs N/N, draw, and an age chip.

**Server › Hardware.**
1. Header: name, critical tag, health, power state, age chip, **action bar** (power ▾, fans, console ▾, Open BMC UI ↗).
2. Status summary tiles: hottest temperature with headroom, fans, PSUs and redundancy, draw (current/peak), power-good N/N.
3. Exceptions list, with anchors.
4. Temperatures (headroom meters), Fans (with owner and lease state from P3), PSUs + chassis power, analog voltages, power-good summary (`<details>`).

**Server › Logs.** Severity filter (default Warning+), SEL / Lifecycle tabs, stacked rows on a phone, and a pager.

**Server › Inventory.** Identity, firmware grouped by component (running, staged, previous), license, **Capabilities** (what this BMC supports and why not).

**Server › Operations** *(P2/P3)*.
- Power panel: current state; allowed actions grouped Safe (On, Graceful shutdown, Graceful restart) vs Forced (Force off, Power cycle, Force restart, admin-only); cooldown timer.
- Fan panel: owner (host curve / lease / BMC AUTO), applied %, lease form (target %, mode, duration 5–120 min, reason), countdown, **End now**.

**Server › Console** *(P4/P5)*. Console frame (see C-14).

**Events.** Filters (server, log, severity, time range); a list grouped by day; repeats collapsed.

**Settings.**
- Side nav: Users, API tokens, Audit log, then (S2–S4) General, Servers, Integrations.
- Each page shows its step-up state as one line at the top, and "Managed by config.yaml" lock badges on read-only fields.

**Auth flows.**
- Sign in → Code → (Enrol: Password → Authenticator → Done) → Step-up (with action context).
- One card, centred, at most 28 rem wide, with the instance name.

**About / Help.** Version + commit (copy block), licences and NOTICE, supported hardware, docs, report a problem, security policy, accessibility statement.

### 5.5 Required states (every data component must have a design for each)

| State | Visual and text rule |
|---|---|
| **Healthy / OK** | Green badge "OK", low visual weight. Healthy should be *quiet*. |
| **Warning** | Amber badge "Warning" + glyph (▲) + the reason ("CPU2 3 °C below warning"). |
| **Critical** | Red badge "Critical" + glyph (✕/!), raised to Needs attention, row highlighted with a left border. |
| **Info** (logs only) | Neutral grey badge "Info". Never green. |
| **Unknown** (health only) | Grey "Unknown" + reason. |
| **Not reported** | Muted italic "Not reported"; suppress whole columns or sections when 100 % unreported. |
| **Not monitored** | A sentence explaining it is a hardware property, not a fault. |
| **Stale** | Stale badge "Stale (last: OK)" + age; values remain visible but carry a stale border pattern (not opacity); a banner at the top of the server. |
| **No data / never polled** | "No data yet" + last error class + "Check BMC address and credentials" link (admin). |
| **Loading / in progress** *(P2+)* | Server-rendered "Pending…" state with a started time; for power, "Waiting for the BMC to report Off (12 s)". No spinners without text. |
| **Partial** | Warning note with a count ("15 of 120 entries read") + Reload. |
| **Error** | Plain-language cause + what to do + correlation ID for the audit. |
| **Empty** | Explain + next step (role-aware). |
| **Disabled action** | Visible but `aria-disabled`, with the reason shown inline: *not supported by this BMC*, *needs admin role*, *not licensed (iDRAC Express)*, *cooldown 42 s*, *lease active*. Never just hide it silently. |
| **Locked (config)** | Lock icon + "Managed by config.yaml (`servers[0].bmc.address`)". |
| **Step-up fresh / needed** | One line: "Changes allowed until 02:49" or "Confirm with your authenticator to make changes". |
| **Console session** | Connecting, Connected (encrypted or unencrypted note), In use by X since T, Idle-timeout warning (2 min before), Disconnected (reason + Reconnect), Unsupported / Needs setup / License (per research §4.4). |
| **Fan lease** | None (host curve), Pending (written, awaiting host ack), Applied (countdown), Cancelled by thermal guard (reason, temperature), Expired. |

### 5.7 Tone and microcopy
- **Calm, specific, short.** Write for a tired person at 3 a.m. Lead with the verdict, then the reason, then the action: "PSU 2 critical: input lost. Check the power cord or PDU."
- Plain verbs on buttons ("Power cycle R240", "Revoke token homepage"), never "OK", "Submit" or "Yes".
- No blame and no exclamation marks. Errors say what happened and what to do next.
- **US English** (decided). Grade-8 reading level for everything except Inventory and Audit details.
- Jargon gets a tooltip or glossary link the first time on a page (SEL, Lifecycle, FQDD, PG, Redfish, lease).
- Times: absolute + relative; the user's display time zone once S2 lands, with UTC available.
- Never a fake reassurance: the empty states state their scope.

### 5.8 Accessibility constraints (non-negotiable)
- WCAG 2.2 AA on every page, in both schemes, at 320–1920 px, and at 200 % and 400 % zoom. The axe gate in CI stays at zero violations.
- Status never by colour alone: always a word plus a glyph.
- Non-text contrast ≥ 3:1 for field boundaries, focus rings, meter ticks and badge borders.
- Focus ring visible in both schemes and **distinct from the warning colour**.
- Targets ≥ 44x44 px on touch layouts; at least 24 px (2.5.8) everywhere.
- Typed confirmation and TOTP fields allow paste (3.3.8). There is no time limit on confirm screens; the cooldown applies to repeat actions, not to reading.
- Live regions: `role=status` for async results (power transition, lease applied); no auto-announcing timers.
- Motion: none needed. Any transition respects `prefers-reduced-motion`. No flashing alarm states.
- Forced-colors and print styles are kept.
- Console: a documented keyboard escape; the serial console is the accessible alternative.
- **AODA:** ship an accessibility statement and a feedback contact (IASR s.11 expects accessible feedback processes for the organisations that deploy it). Note in the docs that the product targets WCAG 2.2 AA, which exceeds the AODA 2.0 AA baseline.

### 5.9 Dark / light
- Dark is the default and light is first-class. Follow the OS until a user preference is set (S2): an explicit `data-theme` on `<html>`, persisted per user.
- Keep the current token architecture (`--bg`, `--surface`, `--text`, `--muted`, `--accent`, `--ok/--warn/--crit`, `--stale-*`, `--on-accent`).
- Add `--field-border`, `--info`, `--danger-bg` and `--focus` distinct from `--warn`.
- Dark backgrounds stay off-black (`#111418`); no pure white text on them (current `#e6e9ed` is fine).
- Severity colours are re-tuned per scheme. Every pair is documented with its contrast ratio in the token file, as `--on-accent` already is.

### 5.10 Density
- **Comfortable** by default for phone and stress use (16 px body, 44 px rows on touch).
- **Compact** table density for the operator fleet table and logs at ≥ 1024 px (32–36 px rows), selectable later as a preference.
- Overview cards for ≤ 6 servers; the table becomes the default above 6.
- Body text ≥ 16 px; meta text ≥ 13 px (today's 12.8 px is the floor, so don't go lower).
- Line length ≤ 75 ch in prose (Settings explanations, Help).

### 5.11 Technical constraints for the designer
- Server-rendered HTML; **strict CSP**, with no inline script or style.
- **Minimal, optional JS**: everything must work without it. A single `'self'` enhancement script is acceptable for Copy, dialog polish and menu dismiss.
- No web fonts from CDNs (offline, NFR-6); a system font stack. Embedded SVG icons only.
- No SPA patterns: no client-side routing and no skeleton screens that depend on JS. "Loading" is a server-rendered pending state plus a refresh.
- Every interactive state must be expressible as a URL or a POST form.

## 6. Acceptance criteria for the mockups

Mockups are accepted only when **all** of the following hold. Each item is testable by review, or by the Playwright and axe gate once implemented.

**Coverage**
1. Mockups exist for: Overview (healthy, degraded, 1 stale, > 6 servers table), Server Hardware (healthy, critical, stale, no data), Logs (desktop + 390 px stacked), Events, Inventory with Capabilities, Operations/Power, Fans/lease (none, pending, applied, guard-cancelled), Serial console, Graphical console (connected, in use, needs setup, unsupported), Settings Users / Tokens / Audit / user detail, every confirm and step-up variant, Sign in / Code / Enrol (3 steps) / rate-limited, error 403/404/500, About/Help, first-run empty state.
2. Each of those comes in **dark and light**, at **1440, 820 and 390 px**. Overview, Server and Logs also at **320 px**.
3. Every component in §5.6 is shown with all its states (§5.5), including disabled-with-reason.

**Triage and hierarchy**

4. **5-second test:** on Overview and Server at 390x844, the health verdict, the worst item, and the data age are visible **without scrolling**.
5. On Server › Hardware at 390x844, at least one sensor value (the hottest temperature with headroom) is above the fold.
6. A healthy overview uses less vertical space than a degraded one. Non-OK items always appear before OK items.
7. Needs attention covers both current sensor problems and Warning+ events from the last 24 h, and its empty state states its scope.
8. Power-good signals are summarised (N/N) and never shown as volts.

**Dangerous actions (P2–P5)**

9. Every destructive or irreversible action goes through C-11. The title names verb + target; Cancel is the default focus; the confirm button names the action.
10. Forced power actions and actions on `critical`-tagged servers require typing the server name and show a "what goes down" list. The safe and forced groups are visually separated, and the forced group uses the danger style.
11. Step-up (C-12) always shows the pending action and target, and is skipped when the window is fresh.
12. Every disabled action shows *why* (role, capability, license, cooldown, lease) in visible text.
13. After an action there is a pending state, then a verified result showing the audit record ID (FR-10).
14. The fan lease shows owner, applied %, enforced minimum, countdown and **End now** without step-up. The target % control works with the keyboard alone and with a single pointer (no drag-only control).
15. The console frame keeps Disconnect visible at all times, documents the keyboard-release chord, shows encryption state and session limits, and links to the serial console as the accessible alternative.

**Accessibility**

16. Every text and badge pair is annotated with a contrast ratio of at least 4.5:1 (text) or 3:1 (non-text, including field borders and focus rings), in both schemes.
17. No status relies on colour alone; a greyscale export of each mockup remains fully interpretable.
18. Touch targets are at least 44x44 px at ≤ 820 px. Focus-ring styles are drawn for every interactive component and are distinct from the warning colour.
19. Reading and focus order are annotated for Overview, Server, Confirm and Console. There is a single h1 per page and the heading levels don't skip.
20. The 320 px mockups show no horizontal page scroll; log and event tables use the stacked variant.

**Content and consistency**

21. Copy is US English throughout, with no "licence", "enrolment" or "colour". `<title>` and h1 come from one string.
22. Times are shown absolute + relative with a time-zone label; the age chip has all 3 states.
23. Secrets are monospace, grouped, carry a usage hint, and state "shown once".
24. Audit entries read as sentences, with the action code secondary.
25. Firmware is grouped by component with a state legend; no column is empty on every row.

**Open-source polish**

26. The first-run checklist and role-aware empty states are designed.
27. Help, glossary entry points, About (version + commit copy block, supported hardware, report a problem, security policy, accessibility statement) and an instance-name slot on Sign in are present.
28. The phone header is a single row with a Menu sheet; the server switcher shows health per server.

**Technical feasibility**

29. Every interaction is achievable with server-rendered HTML and POST/GET forms; anything needing JS is marked "enhancement" and has a no-JS fallback.
30. No external fonts, images or CDNs. Icons are a single embedded SVG set with consistent stroke and size.
